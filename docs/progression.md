# 経験値・レベルアップ・ステージ結果

## 1. 根拠

基準: `docs/game-design.md` §5.3（レベルアップ）と§9.2（リザルト）。本書は設計案、現行実装、未決定事項を分けて記録する。

## 2. 経験値報酬

設計書 §5.3 の初期案:

| 行動結果 | 経験値 |
|---|---:|
| 敵にダメージを与える | +10 |
| 敵を撃破する追加報酬 | +20 |
| ボス撃破追加報酬 | +10 |

実装: `src/application/perform-attack.ts`

- プレイヤーが開始した戦闘で、プレイヤー側の攻撃イベントが敵に1以上のダメージを与えた場合、その攻撃イベントごとに+10 EXP。
- 対象のHPが0になった場合に+20 EXP。
- マップobjectiveが `defeat_boss` で、撃破対象IDが `targetUnitId` と一致した場合のみ、さらに+10 EXP。
- ミス、および命中してもダメージ0の場合は+10 EXPを付与しない。これは「ダメージを与える」という文言に沿った実装解釈で、1回の戦闘行動内に複数のダメージイベントがある場合はイベント数分付与する。
- 敵AIの攻撃ではプレイヤーにEXPを与えない。味方同士の攻撃も現行ルールで許可していない。
- 攻撃側ユニットが反撃で撃破され、次状態に残らない場合はEXPを適用しない（現行の撃破済みユニット除去モデルによる制約）。

## 3. レベルアップと成長判定

実装: `src/domain/progression/level-up.ts`

- 経験値が100以上になったら100を差し引き、レベルを1上げる。
- 100を超える経験値が一度に付いた場合は、100ごとに複数回レベルアップする。
- 各レベルアップ時にHP、力、魔力、技、速さ、幸運、守備、魔防を独立して成長判定する。
- 成長率0〜100を、0〜99の乱数ロールと比較する。
- レベルアップごとに8能力それぞれ1回のXorshift32乱数を消費する。成長率0・能力上限到達済みの能力でもロールを消費し、順序を安定させる。
- RNG stateは戦闘で消費した乱数の後から連続して進め、GameStateSnapshotの既存 `rngState` として保存する。
- HP成長は最大HP（`stats.hp`）を増加させる。**現在HPは増加させない**（無料回復を行わない暫定解釈）。

## 4. クラス能力上限の暫定データ

設計書は「現在クラスの上限を超えない」とする一方、v1.0に数値の上限テーブル／クラス定義データはない。

そのため `src/content/classes.ts` の現行プロトタイプでは、すべての試作クラスに同じ仮上限を一時的に設定している。

- HP: 60
- 力・魔力・技・速さ・幸運・守備・魔防: 30

これは正式なクラス上限やバランス値ではない。クラスごとの上限値が決まったら置き換える。未定義クラスには暗黙の上限を与えずエラーにする。

## 5. ステージ結果UI

戦闘結果が勝利／敗北に確定したとき、現在のマップのリザルト概要を表示する。

- 勝敗
- 敵撃破数（マップ初期enemy deployment数と現在生存敵数の差）
- 生存味方数
- 生存味方ごとのレベル、現在EXP／100、現在HP／最大HP

設計書 §9.2 が挙げる撃破数・経験値・レベルアップの表示に加え、章定義されたアイテム報酬と次章開始導線を実装した。戦闘全体の詳細統計・撃破者一覧・加入／会話イベントは未実装。経験値・能力値・レベル・報酬アイテムは既存GameStateへ反映し、別のセーブフィールドは追加していない。

## 6. セーブ互換性

- `GameUnit` は `level`、`experience`、`stats`、`growthRates` を保存し、`GameStateSnapshot` は既存の `rngState` を保持する。
- 現行の `SAVE_VERSION` は3。saveVersion 1／2からの既存migrationを維持する。
- クラスチェンジ処理は既存フィールド（`classId`、`level`、`experience`、`stats`、`currentHp`、`inventory`）を更新するだけで、専用のGameState fieldを追加しない。
- GameState validatorはEXPを0〜99に制限し、レベルアップ前の未処理100 EXPが保存されることを防ぐ。
- クラス定義の静的な数値変更だけならsnapshot schema変更は不要。新フィールドを追加する場合は、現行v3からのmigrationとvalidator／JSON／backup互換テストを先に設計する。

## 7. クラスチェンジ基盤

正式仕様の未決定項目、現行仮実装との相違、段階的な決定・実装順は [クラスチェンジ仕様・未決定事項と実装計画](class-promotion.md) に集約する。

根拠: 設計書 §5.4（クラスチェンジ）・§5.5（初期クラス案）。正式決定の台帳と実装順は [class-promotion.md](class-promotion.md) を参照。

設計書が示す昇格先を `src/content/classes.ts` にIDとして定義した。

| 基本職ID | 昇格先ID |
|---|---|
| swordsman | swordmaster |
| mercenary | hero |
| fighter | warrior |
| soldier | general |
| cavalry | paladin |
| archer | sniper |
| mage | sage |

実装:
- `src/domain/progression/class-change.ts` の `applyClassPromotion` は、味方ユニット、元クラス一致、Lv.10以上、専用アイテム所持を検証する。
- 専用アイテムIDを所持品から1個消費し、昇格後クラスIDへ変更、レベルを1にする。
- 能力ボーナスと昇格先上限は `ClassPromotionDefinition` で明示的に受け取る。ボーナスは上限まで適用し、既存能力が上限を超えていても能力を減少させない。
- HPボーナスは最大HPだけに加算し、現在HPは維持する。
- クラスチェンジ後のEXPは設計書に記載がないため、設定側が `preserve` または `reset` を必ず指定する。
- `src/application/perform-class-change.ts` は昇格先テーブルと照合し、対象ユニットだけを更新した新しいGameStateを返す。

### 試作コンテンツとUI接続

- `src/content/items.ts` に `promotion_seal`（表示名「クラスチェンジの証」）を定義。所持品配列は既存 `inventory: string[]` を利用し、武器IDとアイテムIDを同じ枠で扱う。
- chapter-01 の新規初期状態では、味方01（剣士）に証を1個だけ付与する。これは動作確認用の仮配布で、章報酬ルールではない。
- `src/App.tsx` に武器以外の所持品表示とクラスチェンジパネルを追加。対象ユニットが味方、基本職Lv.10以上、証を所持し、自軍フェイズ中の操作可能状態である場合だけ確認ボタンを有効にする。
- 確認後、`performClassChange` を呼び出し、クラス変更・証消費・能力反映を行ってIndexedDBへ保存する。クラスチェンジ自体では `hasActed`／`hasMoved` を変更しない（行動消費の仕様が設計書にないため）。
- 既存saveVersion 2を含む既存セーブへ証は自動付与しない。アイテム配布を含むセーブマイグレーションは行わない。

### 試作ボーナス（暫定）

設計書は能力ボーナスを付与する方針だけを示し、数値を定義していない。UIを動作確認できるよう、クラスごとに次の仮値を設定した。正式なバランス値ではない。

| 基本職 | 仮ボーナス |
|---|---|
| 剣士 | HP+2、技+1、速さ+1 |
| 傭兵 | HP+2、力+1、速さ+1 |
| 戦士 | HP+3、力+2 |
| ソルジャー | HP+2、守備+1 |
| 騎兵 | HP+2、力+1、速さ+1 |
| アーチャー | HP+2、技+2 |
| 魔道士 | HP+2、魔力+2 |

昇格先の仮上限は、レベルアップ時の試作上限と同じHP60／他能力30。昇格時のEXPは保持する暫定方針。移動力・移動種別・使用可能武器は変更せず、基本職から引き継ぐ。昇格後クラスの正式なクラス定義が整うまでの動作確認用である。

所持品とクラスデータはcontent層で管理する。現行の `SAVE_VERSION` は3であり、クラスチェンジ固有のGameState fieldを追加していない。

## 8. 章間引き継ぎ基盤

実装: `src/application/prepare-next-chapter.ts`。

- 前章が `evaluateBattleOutcome(...)=victory` の場合のみ遷移できる。敗北／戦闘中からの遷移は拒否。
- 次章マップの味方配置リストが出撃者と配置先を決める。前章開始時にいた味方IDは前章stateに存在する場合のみ引き継ぎ、撃破済みでstateから除去された味方は復帰させない。
- 次章から新たに加入する味方は、次章初期stateのユニット定義から追加できる。
- 引き継ぎユニットはレベル、EXP、能力値／成長率、クラス、所持品、装備、移動・武器適性を保持する。位置は次章配置へ変更し、移動／行動済みフラグをresetする。
- 敵ユニット、章ID、turn=1、player phase、RNG stateは次章初期stateを採用する。
- 章間HPは設計書に規定がないため、呼び出し側が `preserve`（現在HP維持）または `restore`（次章開始時に最大HPへ回復）を必ず指定する。
- GameStateSnapshotの形は変えず、現行 `SAVE_VERSION` 3のまま。作成された次章stateは既存validatorで検証する。
- `src/content/chapters.ts` に章ID・表示名・マップ・初期state・クリア報酬を登録し、保存された `chapterId` から対応するマップを選択してセーブを検証／復元する。
- `src/application/apply-chapter-rewards.ts` は勝利後にだけ、章データが明示したアイテム報酬を指定された生存味方へ付与する。未定義アイテム、非生存／非味方の受取人、1〜5以外の数量、所持品5枠超過は拒否する。
- リザルト画面から次章を開始すると、報酬付与→`prepareNextChapter`→章切替→既存IndexedDB auto slot保存を行う。章間引き継ぎ自体はsnapshot fieldを追加せず、現行saveVersion 3の形式を利用する。
- `chapter-02` は同じ味方／敵構成を用いた遷移動作確認用の試作マップ。正式シナリオ・敵配置・報酬は定義していない。両試作章の `clearRewards` は空配列。
- 現在HPは設計未決定のため、UIでは暫定的に維持する。乱数stateは章をまたいで引き継ぐ。
- 詳細戦闘統計、会話／加入イベント、キャンペーン選択・分岐／解放管理は未実装。

## 9. 未決定・未実装

- クラス別の正式な能力上限値と昇格時の能力ボーナス。
- 昇格時EXPの扱い（preserve／reset）、昇格後クラスの移動・武器データ。
- 正式なクラスチェンジアイテムの入手／章報酬／配布ルール、章間の利用タイミング（現在はchapter-01新規状態への仮配布のみ）。
- HP成長時に現在HPも回復するかどうか。
- 1回の攻撃行動で複数回ダメージを与えた際の経験値を、攻撃イベント単位とするか行動単位とするか（現行はイベント単位）。
- 主人公／ボス役割の正式データ。ボス経験値はobjectiveのtargetUnitIdを利用。
- 詳細戦闘統計、撃破者一覧、会話／加入イベント、キャンペーン選択・分岐／解放管理。
