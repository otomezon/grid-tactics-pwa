### 昇格経路と条件

`src/content/classes.ts` は次の7経路を登録している。

| 基本職ID | 昇格先ID |
|---|---|
| swordsman | swordmaster |
| mercenary | hero |
| fighter | warrior |
| soldier | general |
| cavalry | paladin |
| archer | sniper |
| mage | sage |

現行UI／application／domainは、player faction、player phase、戦闘継続中、対象基本職に昇格先定義があること、Lv.10以上、`promotion_seal` 所持を確認する。domainは元クラスと昇格先の対応も再検証し、証を所持品から1個消費する。敵ユニットには適用しない。昇格後クラスには現行の昇格先定義がないため、現在は一段階の昇格で止まる。

2026-11-10にCP-12の推奨案を採択した。現在のUI／application／domainは、自軍フェイズ中かつ対象ユニットの `hasMoved`／`hasActed` がともにfalseの場合だけ昇格を許可する。成功時は `hasActed` をtrueにし、そのユニットの当該フェイズの行動を消費する。domain／applicationの両方で条件を検証する。

### アイテムとセーブ

- アイテムIDは `promotion_seal`、表示名は「クラスチェンジの証」。既存の `inventory: string[]` に格納し、同じIDの重複で個数を表す。
- 2026-11-10にCP-13の推奨案を採択し、新規初期状態の味方01への試作付与を廃止した。証は明示的な章報酬／イベント定義でのみ配布する。現時点で章報酬は未登録のため、通常の初期キャンペーンではまだ入手できない。

### 3.3 同条件の仮想戦闘比較（PR #82）

開発専用の実セーブsnapshotベンチは、昇格前snapshotのcontrol枝と昇格command後のpromotion枝について、同じ登録済み章マップ・敵ユニット・位置・地形・装備武器・開始RNGを使った1回の戦闘サンプルを実行できる。実装は既存の `src/application/perform-attack.ts` を再利用し、既存forecastと `CombatResult.events`、戦闘後HP、EXP／レベルアップ、終了RNGを表示する。比較条件が一致しない枝や、武器射程内に生存敵がいないsnapshotは対象外とする。

CP-12により昇格はその自軍フェイズの行動を消費する。したがって戦闘比較のpromotion枝は、昇格コマンドが返した `hasActed=true` のstateを保持したうえで、**比較専用の切り離したコピーだけ**次の自軍行動機会を模して `hasActed=false` に戻してから攻撃を実行する。これは昇格直後の同一ターンに攻撃できるという意味ではない。enemy phase、ターン経過、移動、敵AI、複数攻撃機会、複数seedの勝率／分布はシミュレートしない。

この結果は現行戦闘ロジック上の単一seed比較サンプルであり、合成E2E fixtureは実プレイデータではない。全21ケースの実プレイ統制評価やCP-04／05の数値承認を代替せず、現行の昇格値・クラス上限・武器性能・戦闘距離の試作設定も正式化しない。両枝ともブラウザ内の開発用メモリコピーだけで処理し、import元snapshot、GameState、IndexedDB、RNG永続値は変更しない。

### セーブ内プレイ履歴の根拠サマリー（実装）

snapshotベンチは読み込んだsnapshotの既存記録から、キャンペーン戦闘ログの件数・記録章数・行動／攻撃／敵行動／章結果の内訳と、選択ユニットの行動／攻撃／被標的件数を集計する。加えて、`campaignUnitBattleRecords`の選択ユニット分（攻撃・strike・命中・与ダメージ・撃破・EXP）を表示／CSVへ記録する。比較候補の出所を人が評価するための補助であり、ファイルの真正性、改変有無、完全な実プレイ履歴を自動認定するものではない。

- `campaignBattleLog`は元saveVersion 9以上、`campaignUnitBattleRecords`は元saveVersion 3以上で追跡対象として表示する。元バージョンが対象外なら「未追跡」とし、0件と区別する。
- 記録が0件でも未プレイとは限らない。古いセーブの移行では、保存されていなかった過去の行動を推測・補完しない。
- `campaignBattleLog`は最大5,000件を保持し、上限到達後は古い行から配列外へ落ちる。ベンチは保存件数／上限、先頭・末尾sequence、保存配列内のsequence欠番数を表示／CSVへ出力する。上限到達は切り捨てが起きた可能性を示すだけで、正確な切り捨て有無を単独では判定しない。欠番数は保存中に見える連番の差であり、欠落した行動の種類・内容を推測しない。
- これらの集計は既存snapshotの読み取りだけで、GameState／RNG／IndexedDB／autosave／saveVersionは変更しない。利用者申告の「実プレイ由来」区分も引き続き自己申告であり、この集計はその検証ではない。

### 3.4 複数seedの独立戦闘サンプル（PR #83）

実セーブsnapshotベンチは単一seedの比較に加え、20／100／250個の決定論的seed系列でcontrol／promotionをペア比較できる。seed系列は元snapshotの初期RNG stateから固定saltで分離したXorshift32 streamにより生成し、各seedを両枝へ同じ値で渡す。両枝の戦闘は既存 `performAttack` を使用する。

各試行は元snapshotをコピーし直した独立の1戦闘であり、HP、敵HP、EXP、撃破状態、装備、位置、turnを次の試行へ持ち越さない。集計するのは攻撃strike単位の命中率／命中時必殺率、平均与ダメージ、対象敵撃破率、平均反撃被ダメージ、反撃後の生存率、平均戦闘後HP。対象敵撃破率と攻撃側生存率には、各seedにつき1つの二値結果を観測単位とした95% Wilson score区間を併記する。strike単位の命中率／必殺率には、1戦闘内の複数strikeが独立観測ではないため、この区間を付けない。promotion側はCP-12の行動消費を守り、次の自軍行動機会を模した比較用コピーだけで攻撃可能にする。

この反復は「固定された初期配置から実行する単発戦闘条件の乱数感度確認」であり、敵軍フェイズ、敵AIの移動・標的選択、地形移動経路、複数ターン、回復・消耗資源、章クリア率をシミュレートしない。したがって全21ケースの統制プレイテスト、実際のプレイヤー体験、CP-04／05の正式な数値承認を代替しない。Playwrightの合成fixtureでの結果は実プレイ証拠として扱わない。

同じseedをcontrol／promotionへペア適用するため、各二値指標についてペア結果の内訳も保持する。「controlのみ発生」「promotionのみ発生」「両方で発生」「どちらでも発生せず」をそれぞれ数え、promotionのみとcontrolのみの件数差をsampleCountで割ったpercentage-point差を表示／CSVへ出力する。敵撃破・生存のほか、敵軍phaseの標的対象・本人生存・敗北・全滅・次自軍phase進行を対象とする。イベント発生が不利な指標（敗北／全滅など）では、発生件数が少ない枝の方が望ましい。これはペア内訳の記述統計であり、p値・信頼区間・有意差判定ではない。

### 3.5 21ケースmatrixの候補整理・CSV記録（PR #84）

開発専用snapshot benchは7基本職×低位／中央値／上位の21ケース候補matrixを表示できる。各基本職について、昇格比較可能な候補が3件以上あるだけでなく、異なるunit IDを持つ候補ユニットsnapshotが3件以上必要である。同じセーブ・同じunit IDを別ファイル名で読み込んでも1件として数え、同じ候補ユニットを低位／中央値／上位の複数profileへ割り当てない。同じセーブ内の異なるunit IDは別候補として扱う。候補カバレッジ表には候補ユニット数・昇格比較可能数・異なるユニットsnapshot数・履歴ログ／味方別累計を持つ候補数を表示する。8能力の同クラス内順位の平均から25%／50%／90%に近い候補を仮提案する。これは候補選択補助であり、自動的にprofileやプレイテスト結果を確定しない。人が各caseの候補・敵・条件を確認し、候補の重複・昇格条件不成立・射程内敵なし・候補不足は実行対象から除外する。上位profileは実測分布内の上位であり、正式cap付近を意味しない。異なるユニットsnapshotは別キャンペーン／別プレイの証明ではないため、同じキャンペーン内の別ユニットや別時点のsaveを書き出した場合もその由来を別途記録する。

21ケースの一括実行は、既存戦闘処理を使う独立した単発戦闘のseed反復に加え、別枠で敵軍phase 1回のseed反復を各caseで実行するもの。control／promotionは各seedを同じペアで受け、各試行は元snapshotから開始する。敵軍phaseの標的率・生存率・敗北結果率・全滅率・次phase進行率など、各seedにつき1つの二値結果となる指標にも95% Wilson score区間を表示／CSV出力する。これはcontrol／promotionそれぞれの率の試行数による推定幅であり、両者の差の信頼区間や統計的有意差を示さず、別の初期配置や実プレイヤーの行動差も含まない。strike単位の命中率／必殺率は同一戦闘内の依存した複数観測なのでWilson区間を付けない。敵軍phase・移動・複数turn・章攻略は再現しない。さらに各seedの二値結果をペアで集計し、controlのみ／promotionのみ／両方／どちらもなしの件数と、promotionのみ−controlのみのpercentage-point差を画面／CSVへ記録する。この差は対応seed内の発生頻度差であり、統計的有意差判定ではない。結果CSVはcase識別情報、候補snapshot fingerprint、ユニット8能力、敵／マップ／turn／RNG、seed範囲、試行数、control／promotion指標と該当する95%区間、ペア結果内訳、データ区分を記録する。

データ区分の「実プレイ由来」は利用者申告であり、アプリによる真正性検証ではない。未確認または合成fixtureを実プレイ記録へ転記しない。CSVは明示的なdownload操作でのみ出力され、snapshot／結果はメモリ上でのみ処理する。従来どおりGameState・IndexedDB・自動保存・network送信は変更しない。


### 3.6 実セーブ候補の証拠台帳CSV（PR #161／#162）

実セーブsnapshotを読み込んだ時点で、21ケースのseed反復を実行する前でも「候補・履歴根拠CSV」を書き出せる。これは候補の収集状況と、比較に使う前の確認を記録する台帳であり、21ケースの戦闘結果CSVとは別ファイルである。

- 同一の正規化済みセーブ内容＋同一unit IDを複数ファイルから読み込んだ場合は1行へまとめる。source file名・export日時・元／正規化saveVersion・migration有無は読み込み元一覧として保持する。異なるunit IDは別候補となるが、同一campaignからの候補かどうかは判定しない。
- 台帳にはクラス・Lv／EXP・8能力・HP・位置・フェイズ・移動／武器情報・昇格比較可否とその理由を含める。位置座標は0始まり。snapshot fingerprintは照合用の短い表示ラベルであり、暗号学的ハッシュや改変検出値ではない。
- campaignBattleLog／campaignUnitBattleRecordsは元saveVersionに応じた追跡可否と件数／累計を分けて記録する。未追跡と追跡対象の0件、味方別累計の追跡対象だが対象unit記録なし、を区別する。
- 保存済み記録の有無は真正性・完全性・異なるcampaignの証明ではない。実プレイ区分も利用者申告のままであり、CSVはこれを自動判定しない。
- CSVはユーザー操作によるダウンロードのみ。候補・履歴はメモリ上で扱い、GameState／RNG／IndexedDB／saveVersion／ネットワーク送信へ影響しない。

### 3.7 実プレイ記録用CSVテンプレート（PR #163）

21ケースすべての候補・敵・条件を人が確認した後、control／promotionの2枝を持つ42行の手動観測テンプレートを書き出せる。ケース識別・候補由来・元snapshotの開始条件と昇格前ユニット／比較敵情報だけを埋め、実セッションID・実行日時／commit／seed・昇格後の実測値・攻撃／防御／戦術／敵軍phaseの観測結果・所見は空欄とする。現在のprototypeボーナス／上限やseed反復シミュレーション結果は転記しない。matrixの「実プレイ由来」は利用者申告であり、真正性の検証ではない。テンプレートは実プレイの実施・数値承認を意味しない。明示的なCSV downloadのみで、GameState／RNG／IndexedDB／saveVersion／ネットワーク送信には影響しない。

### 3.8 手動実プレイ記録CSVの再取込・ペア監査（PR #164）

PR #163で出力した42行の記録用CSVを、ベンチ画面の「記入済み実プレイ記録CSVを確認」から再取込できる。監査はCSVの構造と記入内容だけを対象とし、次を表示する。

- ファイルはブラウザメモリ内でだけ解析し、明示的な破棄またはページ再読込で消える。GameState／RNG／IndexedDB／自動保存／saveVersion／network送信は変更しない。

### 3.9 手動記録欄の完全性表示（PR #165）

手動CSVの120列を `src/application/promotion-manual-playtest-worksheet-schema.ts` で一元管理し、出力側／取込監査側で共有する。監査では列不足をテンプレート構造エラーとして扱い、未入力値とは分ける。受理された枝ごとに入力済み／未入力の観測欄IDを展開でき、全受理枝行について列ごとの入力件数を一覧表示する。

未入力項目は必須条件ではなく、任意・条件依存の観測欄を含む記入状況である。入力率で実プレイ完了・観測の正確性・真正性・独立campaign・CP-04／05の承認を判定しない。処理はブラウザメモリ内に限定し、CSV内容を永続化・送信せず、GameState／RNG／IndexedDB／saveVersionを変更しない。

## 4. 保存データ互換性の方針

現在の `GameUnit` は `classId`、`level`、`experience`、`stats`、`currentHp`、`movementType`、`move`、`usableWeaponTypes`、`inventory`、`equippedWeaponId` を保存する。静的なクラス定義・ボーナス表をcontent層へ追加するだけなら、snapshot schemaの変更は不要であり、既存のGameUnitフィールドだけを使う変更ではsaveVersionを上げずに済むが、現行saveVersion 10では、キャンペーン累計戦績・章間選択・キャンペーン戦闘履歴などもsnapshotに保持する。クラスチェンジ自体は既存のGameUnitフィールドを使い、専用の保存フィールドを追加していない。

ただし、クラス変更履歴、昇格回数、ユニット単位の例外値、移動・武器データの新規フィールドなどを `GameUnit`／`GameStateSnapshot` に追加する判断をした場合は、保存設計を先に更新し、現行saveVersion 10から次versionへの明示的なmigration・validator・export/import・backup復元テストを実装する。saveVersion 4への更新はキャンペーン累計戦績を追加した過去の移行段階であり、現在はv1〜v9からv10への移行を維持している。昇格回数やクラス変更履歴を追加したものではない。セーブに保存済みの能力値や所持品を、クラス定義変更を理由に起動時に無断で再計算しない。

## 8. 開発専用の実セーブsnapshot比較ベンチ

Vite開発サーバーの `http://localhost:5173/?promotion-snapshots=1` では、アプリのセーブ管理から書き出したJSONを複数読み込み、実際のユニットsnapshotを比較できる。

- 対応形式はportable envelope version 1。現在のアプリから書き出すsnapshotは `GameStateSnapshot.saveVersion: 10` であり、入力時はsaveVersion 1〜9を現行v10へmigrationしたうえで、章IDを既存chapter registryから解決し、対象mapに対して `isValidGameStateSnapshot` を適用する。不正なJSON、未対応version、未登録章、validator不合格は拒否する。
- 対象はsnapshot内の出撃中の味方で、現行7基本職、Lv.10以上のユニット。比較コマンドを実行するには自軍フェイズ、未移動・未行動、証を追加できる所持品空き（または証を既に所持）が必要。条件を満たさない候補は理由を表示する。
- 同一クラスの読み込みsnapshotが3件以上ある場合、各能力の同クラス内順位の平均を参考percentileとして表示する。3件未満は「分布データ不足」とし、low／median／highを自動選択しない。ユーザーは試験記録で候補を判断する。
- controlは読み込んだ元snapshot、promotionは同じsnapshotから作る切り離しコピーに既存 `performClassChange` を実行した結果。セーブに証がない場合はコピー内だけに試験用 `promotion_seal` を一時追加して消費する。これはCP-13の報酬決定でも、実セーブへの付与でもない。
- UIは能力8項目、要求ボーナス／実増加／仮上限、クラス・Lv・EXP、最大／現在HP、移動／武器／装備、行動消費、RNG不変を表示する。PR #82では既存 `performAttack` を再利用した単一seedの戦闘比較、PR #83では20／100／250seedの独立単発戦闘集計を追加した。マージ済みPR #86（merge commit `814789b714620fe805aa33281fad77486d4dc200`）では、同じsnapshot・seedから既存 `beginEnemyPhase`／`runEnemyPhase` を使う敵軍phase 1回のpaired比較を追加した。敵行動数／攻撃数、選択ユニット標的率・被害・生存率、味方全体被害／撃破、全滅率、次phase進行率を表示する。
- 読み込んだファイルと候補はReactのメモリだけに保持し、IndexedDB・GameState・自動保存・saveVersionを読み書きしない。ネットワーク送信や永続キャッシュも行わない。リロードまたは破棄操作で消去する。これは開発サーバー専用で、本番ビルドでは表示されない。

単発攻撃のseed反復は移動・敵軍phase・複数turnを含まない。PR #86の敵軍phase比較は既存敵AIの行動を1 phaseだけ再現し、controlは行動を見送る枝であるため、昇格せず別の行動を選んだ場合との比較ではない。いずれも候補整理と既存ロジック上の影響確認を補助するものであり、実際のプレイヤー操作を含む完全な戦闘／章攻略、統制した実プレイ21ケース、CP-04／05の数値承認を代替しない。

数値ボーナス・クラス別上限・具体的な章報酬／受取人／数量は未決定のままとする。`docs/game-design.md` 原文、セーブ形式、依存関係は変更しない。現在の仮ボーナス・仮上限を正式バランスとして扱わない。昇格時の行動消費と証の初期自動付与廃止は、採択済みの非数値ベースラインに沿った実装である。
