## 1. 設計書に記載済みの基本方針

`docs/game-design.md` §5.4–§5.5 に明記されているのは次の範囲。

| 項目 | 設計書の記載 |
|---|---|
| 対象レベル | 基本職Lv.10以上 |
| 消費 | 専用クラスチェンジアイテムを消費 |
| 昇格先 | クラスごとに定義 |
| 初期版の経路 | 各クラス1つの昇格先。分岐昇格は拡張扱い |
| 昇格時の成長 | 能力ボーナスを付与し、上限を昇格先クラスのものへ変更 |
| 昇格後レベル | 昇格先クラスのレベルを1から表示し、その後もレベルアップ可能 |
| クラス案 | 剣士→ソードマスター、傭兵→勇者、戦士→ウォーリア、ソルジャー→ジェネラル、騎兵→パラディン、アーチャー→スナイパー、魔道士→賢者 |

設計書は初期実装向けの提案であり、能力上限・能力ボーナスの数値、EXP端数、HP回復、昇格後の移動・武器性能、アイテム配布や行動消費までは決めていない。

## 2. 現行プロトタイプの確認済み挙動

以下は2026-11-10時点のソースとテストで確認した実装事実であり、正式仕様として承認されたことを意味しない。

### 昇格経路と条件

`src/content/classes.ts` は次の7経路を登録している。

| 基本職ID | 昇格先ID |
|---|---|
| swordsman | swordmaster |
| mercenary | hero |
| fighter | warrior |
| soldier | general |
| cavalry | paladin |
| archer | sniper |
| mage | sage |

現行UI／application／domainは、player faction、player phase、戦闘継続中、対象基本職に昇格先定義があること、Lv.10以上、`promotion_seal` 所持を確認する。domainは元クラスと昇格先の対応も再検証し、証を所持品から1個消費する。敵ユニットには適用しない。昇格後クラスには現行の昇格先定義がないため、現在は一段階の昇格で止まる。

2026-11-10にCP-12の推奨案を採択した。現在のUI／application／domainは、自軍フェイズ中かつ対象ユニットの `hasMoved`／`hasActed` がともにfalseの場合だけ昇格を許可する。成功時は `hasActed` をtrueにし、そのユニットの当該フェイズの行動を消費する。domain／applicationの両方で条件を検証する。

### 仮の能力値と昇格時処理

`src/content/classes.ts` の現在値:

| 基本職 | 仮ボーナス |
|---|---|
| 剣士 | HP+2、技+1、速さ+1 |
| 傭兵 | HP+2、力+1、速さ+1 |
| 戦士 | HP+3、力+2 |
| ソルジャー | HP+2、守備+1 |
| 騎兵 | HP+2、力+1、速さ+1 |
| アーチャー | HP+2、技+2 |
| 魔道士 | HP+2、魔力+2 |

すべての基本職・昇格先に同一の試作上限（HP 60、その他7能力30）を与えている。現行domainはボーナスを昇格先上限まで適用し、既存能力が上限より高い場合も能力を減らさない。HPボーナスは最大HPのみを増やし、現在HPは維持する。

昇格後レベルは1。EXPは採択済みCP-07に従い0〜99の端数を保持する。HPボーナスは採択済みCP-08に従い最大HPだけへ加算し、現在HPは維持する。PR #32の境界テストでEXP 0／99、現在HP 1／満タン、最大HP上限直前のボーナス制限と現在HP維持を検証した（CI run #503: 22 test files／146 tests、Chromium E2E 11件成功）。PR #36のE2Eでは73 EXPを持つユニットについて、現行確認画面が暫定ボーナス・レベル1化・EXP保持・証1個消費・行動消費を説明し、昇格確定後とリロード後もEXP 73が保持されることを検証した（CI run #510: 22 test files／147 tests、Chromium E2E 11件成功）。このテストは現行UIと採択済みCP-07の整合性を確認するもので、CP-15の最終表示要件を確定するものではない。移動力 `move`、移動種別 `movementType`、使用可能武器 `usableWeaponTypes`、装備武器 `equippedWeaponId` は、採択済みCP-09／10に従い正式な昇格先データができるまで元ユニットの値を維持する。CP-12に従い昇格前は未移動・未行動を要求し、昇格後は `hasActed=true` とする。昇格先クラス固有の移動・武器データはまだモデル化されていない。

### アイテムとセーブ

- アイテムIDは `promotion_seal`、表示名は「クラスチェンジの証」。既存の `inventory: string[]` に格納し、同じIDの重複で個数を表す。
- 2026-11-10にCP-13の推奨案を採択し、新規初期状態の味方01への試作付与を廃止した。証は明示的な章報酬／イベント定義でのみ配布する。現時点で章報酬は未登録のため、通常の初期キャンペーンではまだ入手できない。
- 既存セーブへの自動付与は行わない。既に所持している証は既存インベントリのまま保持する。セーブスキーマ変更やmigrationは不要。
- 現行処理はクラスチェンジ専用の `GameStateSnapshot`／`GameUnit` フィールドを追加しない。現行の `SAVE_VERSION` は3であり、クラスID・レベル・EXP・能力・所持品・移動／武器情報は既存フィールドを使う。

### 3.2 現行contentから作った合成シナリオの扱い

`src/test-support/class-promotion-balance-scenarios.ts` は、現行第1章の共通成長テンプレートを1024個の固定Xorshift32 seedでLv.10まで成長させ、10／50／90パーセンタイルの3 profileを選び、7経路×3 profileの昇格previewを作るテスト用fixtureである。これはdomain計算の再現性・21組合せの網羅確認にのみ使う。実際のプレイヤーsave／プレイ履歴／クラス別成長傾向を表すものではなく、能力上限・ボーナスのバランス妥当性も証明しない。

## 4. 保存データ互換性の方針

現在の `GameUnit` は `classId`、`level`、`experience`、`stats`、`currentHp`、`movementType`、`move`、`usableWeaponTypes`、`inventory`、`equippedWeaponId` を保存する。静的なクラス定義・ボーナス表をcontent層へ追加するだけなら、snapshot schemaの変更は不要であり、既存 `SAVE_VERSION: 3` を維持できる見込み。

ただし、クラス変更履歴、昇格回数、ユニット単位の例外値、移動・武器データの新規フィールドなどを `GameUnit`／`GameStateSnapshot` に追加する判断をした場合は、保存設計を先に更新し、旧v3からの明示的なmigration・validator・export/import・backup復元テストを実装する。セーブに保存済みの能力値や所持品を、クラス定義変更を理由に起動時に無断で再計算しない。

## 5. 実装計画

### Stage 0 — 仕様決定

CP-01〜03／06／15は2026-11-12に採択済み。CP-04／05は記入表の21ケース（7経路×3プロファイル）を同条件で比較し、実プレイの戦闘ログとスナップショットを記録する。開発専用試験室の合成fixtureはstat previewの確認用であり、実プレイ試験を代替しない。プレイテストが未実施の数値は空欄のままにし、数値案を作成した後も別途承認を得る。CP-07〜CP-14／CP-16も維持する。

### Stage 1 — クラス定義のデータ化

- クラスID・表示名・能力上限・移動力・移動種別・使用可能武器種を、昇格経路とは分離したcontent定義に整理する。
- 昇格定義は元／先クラス、必要アイテム、能力ボーナス、EXP／HP／装備／行動ポリシーを型で明示する。
- 未定義クラスや不正な数値を暗黙の既定値で補わず、content testで拒否する。
- 現在の仮データを正式値へ昇格させるのは、Stage 0の承認と区別して行う。

### Stage 2 — domain／application

- `applyClassPromotion` を決定済みのポリシーに沿って純粋・不変に更新する。
- レベル、EXP、能力上限、HP、移動、武器適性、装備、アイテム消費、行動フラグを一括して検証する。
- 昇格後に装備中武器が使用不可なら、決定された解除／保持ルールを適用し、違法な状態を残さない。
- application側でphase、対象unit、昇格経路を検証し、他ユニット・reserve・元stateを意図せず変更しない。

### Stage 3 — UI

- 現行プロトタイプの昇格確認画面では、8能力すべての現在値／昇格後予測値／要求ボーナス／上限適用後の実増加量／試作上限を一覧表示する。プレビューとdomainの昇格処理は同じ純粋計算ヘルパーを使い、表示値と確定値の計算差異を避ける。
- 最大HPと現在HP、Lv.10等の現在レベルからLv.1への変化、EXP端数保持、証1個の消費数、移動種別／移動力、武器適性、装備中武器、昇格後の行動消費を確認前に表示する。HPは最大HPのみ加算し、現在HPは回復しない。
- 仮上限を既に超えている既存能力は減少させず、現在値を維持することをプレビューにも表示する。能力ボーナス・上限は試作値であり、正式バランスとして扱わない。
- CP-15の表示要件は採択済み。仮ボーナス・仮上限を使う現在の確認画面は、最終数値・正式なクラス別性能が決定した時点で表示内容と値の出典を再確認する。
- キャンセルはGameState・IndexedDB・UI選択状態を変更しない。
- 確定時だけapplication commandを実行し、既存の保存エラー表示・入力ロックと整合させる。
- スマートフォン幅で確認文・能力差分・ボタンが操作可能であることを確認する。

### Stage 4 — アイテム配布と章進行

- 決定された配布元・章・受取人・数量だけをcontent/reward dataへ設定する。
- 既存の章報酬validator、所持品枠数、控え名簿、章間引き継ぎを再利用し、配布失敗でアイテムを消失させない。
- 初期状態への仮配布を正式配布ルールと混同しない。旧セーブへ自動付与する場合は別途migrationとして設計・承認する。

## 6. 完了条件とテスト計画
