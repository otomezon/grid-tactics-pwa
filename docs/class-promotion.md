## 1. 設計書に記載済みの基本方針

`docs/game-design.md` §5.4–§5.5 に明記されているのは次の範囲。

| 項目 | 設計書の記載 |
|---|---|
| 対象レベル | 基本職Lv.10以上 |
| 消費 | 専用クラスチェンジアイテムを消費 |
| 昇格先 | クラスごとに定義 |
| 初期版の経路 | 各クラス1つの昇格先。分岐昇格は拡張扱い |
| 昇格時の成長 | 能力ボーナスを付与し、上限を昇格先クラスのものへ変更 |
| 昇格後レベル | 昇格先クラスのレベルを1から表示し、その後もレベルアップ可能 |
| クラス案 | 剣士→ソードマスター、傭兵→勇者、戦士→ウォーリア、ソルジャー→ジェネラル、騎兵→パラディン、アーチャー→スナイパー、魔道士→賢者 |

設計書は初期実装向けの提案であり、能力上限・能力ボーナスの数値、EXP端数、HP回復、昇格後の移動・武器性能、アイテム配布や行動消費までは決めていない。

## 2. 現行プロトタイプの確認済み挙動

以下は2026-11-10時点のソースとテストで確認した実装事実であり、正式仕様として承認されたことを意味しない。

### 昇格経路と条件

`src/content/classes.ts` は次の7経路を登録している。

| 基本職ID | 昇格先ID |
|---|---|
| swordsman | swordmaster |
| mercenary | hero |
| fighter | warrior |
| soldier | general |
| cavalry | paladin |
| archer | sniper |
| mage | sage |

現行UI／application／domainは、player faction、player phase、戦闘継続中、対象基本職に昇格先定義があること、Lv.10以上、`promotion_seal` 所持を確認する。domainは元クラスと昇格先の対応も再検証し、証を所持品から1個消費する。敵ユニットには適用しない。昇格後クラスには現行の昇格先定義がないため、現在は一段階の昇格で止まる。

2026-11-10にCP-12の推奨案を採択した。現在のUI／application／domainは、自軍フェイズ中かつ対象ユニットの `hasMoved`／`hasActed` がともにfalseの場合だけ昇格を許可する。成功時は `hasActed` をtrueにし、そのユニットの当該フェイズの行動を消費する。domain／applicationの両方で条件を検証する。

すべての基本職・昇格先に同一の試作上限（HP 60、その他7能力30）を与えている。現行domainはボーナスを昇格先上限まで適用し、既存能力が上限より高い場合も能力を減らさない。HPボーナスは最大HPのみを増やし、現在HPは維持する。

### アイテムとセーブ

- アイテムIDは `promotion_seal`、表示名は「クラスチェンジの証」。既存の `inventory: string[]` に格納し、同じIDの重複で個数を表す。
- 2026-11-10にCP-13の推奨案を採択し、新規初期状態の味方01への試作付与を廃止した。証は明示的な章報酬／イベント定義でのみ配布する。現時点で章報酬は未登録のため、通常の初期キャンペーンではまだ入手できない。
- 既存セーブへの自動付与は行わない。既に所持している証は既存インベントリのまま保持する。セーブスキーマ変更やmigrationは不要。
- 現行処理はクラスチェンジ専用の `GameStateSnapshot`／`GameUnit` フィールドを追加しない。現行の `SAVE_VERSION` は4であり、クラスID・レベル・EXP・能力・所持品・移動／武器情報は既存フィールドを使う。

### 3.3 同条件の仮想戦闘比較（PR #82）

開発専用の実セーブsnapshotベンチは、昇格前snapshotのcontrol枝と昇格command後のpromotion枝について、同じ登録済み章マップ・敵ユニット・位置・地形・装備武器・開始RNGを使った1回の戦闘サンプルを実行できる。実装は既存の `src/application/perform-attack.ts` を再利用し、既存forecastと `CombatResult.events`、戦闘後HP、EXP／レベルアップ、終了RNGを表示する。比較条件が一致しない枝や、武器射程内に生存敵がいないsnapshotは対象外とする。

CP-12により昇格はその自軍フェイズの行動を消費する。したがって戦闘比較のpromotion枝は、昇格コマンドが返した `hasActed=true` のstateを保持したうえで、**比較専用の切り離したコピーだけ**次の自軍行動機会を模して `hasActed=false` に戻してから攻撃を実行する。これは昇格直後の同一ターンに攻撃できるという意味ではない。enemy phase、ターン経過、移動、敵AI、複数攻撃機会、複数seedの勝率／分布はシミュレートしない。

この結果は現行戦闘ロジック上の単一seed比較サンプルであり、合成E2E fixtureは実プレイデータではない。全21ケースの実プレイ統制評価やCP-04／05の数値承認を代替せず、現行の昇格値・クラス上限・武器性能・戦闘距離の試作設定も正式化しない。両枝ともブラウザ内の開発用メモリコピーだけで処理し、import元snapshot、GameState、IndexedDB、RNG永続値は変更しない。

### 3.4 複数seedの独立戦闘サンプル（PR #83）

実セーブsnapshotベンチは単一seedの比較に加え、20／100／250個の決定論的seed系列でcontrol／promotionをペア比較できる。seed系列は元snapshotの初期RNG stateから固定saltで分離したXorshift32 streamにより生成し、各seedを両枝へ同じ値で渡す。両枝の戦闘は既存 `performAttack` を使用する。

各試行は元snapshotをコピーし直した独立の1戦闘であり、HP、敵HP、EXP、撃破状態、装備、位置、turnを次の試行へ持ち越さない。集計するのは攻撃strike単位の命中率／命中時必殺率、平均与ダメージ、対象敵撃破率、平均反撃被ダメージ、反撃後の生存率、平均戦闘後HP。promotion側はCP-12の行動消費を守り、次の自軍行動機会を模した比較用コピーだけで攻撃可能にする。

この反復は「固定された初期配置から実行する単発戦闘条件の乱数感度確認」であり、敵軍フェイズ、敵AIの移動・標的選択、地形移動経路、複数ターン、回復・消耗資源、章クリア率をシミュレートしない。したがって全21ケースの統制プレイテスト、実際のプレイヤー体験、CP-04／05の正式な数値承認を代替しない。Playwrightの合成fixtureでの結果は実プレイ証拠として扱わない。

### 3.5 21ケースmatrixの候補整理・CSV記録（PR #84）

開発専用snapshot benchは7基本職×低位／中央値／上位の21ケース候補matrixを表示できる。各基本職3件以上の候補が必要であり、8能力の同クラス内順位の平均から25%／50%／90%に近い候補を仮提案する。これは候補選択補助であり、自動的にprofileやプレイテスト結果を確定しない。人が各caseの候補・敵・条件を確認し、候補の重複・昇格条件不成立・射程内敵なし・候補不足は実行対象から除外する。上位profileは実測分布内の上位であり、正式cap付近を意味しない。

21ケースの一括実行は、既存戦闘処理を使う独立した単発戦闘のseed反復を各caseで実行するもの。control／promotionは各seedを同じペアで受け、各試行は元snapshotから開始する。敵軍phase・移動・複数turn・章攻略は再現しない。結果CSVはcase識別情報、候補snapshot fingerprint、ユニット8能力、敵／マップ／turn／RNG、seed範囲、試行数、control／promotion指標、データ区分を記録する。

データ区分の「実プレイ由来」は利用者申告であり、アプリによる真正性検証ではない。未確認または合成fixtureを実プレイ記録へ転記しない。CSVは明示的なdownload操作でのみ出力され、snapshot／結果はメモリ上でのみ処理する。従来どおりGameState・IndexedDB・自動保存・network送信は変更しない。

## 4. 保存データ互換性の方針

現在の `GameUnit` は `classId`、`level`、`experience`、`stats`、`currentHp`、`movementType`、`move`、`usableWeaponTypes`、`inventory`、`equippedWeaponId` を保存する。静的なクラス定義・ボーナス表をcontent層へ追加するだけなら、snapshot schemaの変更は不要であり、既存のGameUnitフィールドだけを使う変更ではsaveVersionを上げずに済むが、saveVersion 4ではキャンペーン累計戦績もsnapshotに保持する。

ただし、クラス変更履歴、昇格回数、ユニット単位の例外値、移動・武器データの新規フィールドなどを `GameUnit`／`GameStateSnapshot` に追加する判断をした場合は、保存設計を先に更新し、現行saveVersion 4から次versionへの明示的なmigration・validator・export/import・backup復元テストを実装する。今回のsaveVersion 4への更新はキャンペーン累計戦績の追加であり、昇格回数やクラス変更履歴を追加したものではない。セーブに保存済みの能力値や所持品を、クラス定義変更を理由に起動時に無断で再計算しない。

## 5. 実装計画

### Stage 0 — 仕様決定

CP-01〜03／06／15は2026-11-12に採択済み。CP-04／05は記入表の21ケース（7経路×3プロファイル）を同条件で比較し、実プレイの戦闘ログとスナップショットを記録する。開発専用試験室の合成fixtureはstat previewの確認用であり、実プレイ試験を代替しない。プレイテストが未実施の数値は空欄のままにし、数値案を作成した後も別途承認を得る。CP-07〜CP-14／CP-16も維持する。

### Stage 1 — クラス定義のデータ化

- クラスID・表示名・能力上限・移動力・移動種別・使用可能武器種を、昇格経路とは分離したcontent定義に整理する。
- 昇格定義は元／先クラス、必要アイテム、能力ボーナス、EXP／HP／装備／行動ポリシーを型で明示する。
- 未定義クラスや不正な数値を暗黙の既定値で補わず、content testで拒否する。
- 現在の仮データを正式値へ昇格させるのは、Stage 0の承認と区別して行う。

### Stage 2 — domain／application

- `applyClassPromotion` を決定済みのポリシーに沿って純粋・不変に更新する。
- レベル、EXP、能力上限、HP、移動、武器適性、装備、アイテム消費、行動フラグを一括して検証する。
- 昇格後に装備中武器が使用不可なら、決定された解除／保持ルールを適用し、違法な状態を残さない。
- application側でphase、対象unit、昇格経路を検証し、他ユニット・reserve・元stateを意図せず変更しない。

### Stage 3 — UI

- 現行プロトタイプの昇格確認画面では、8能力すべての現在値／昇格後予測値／要求ボーナス／上限適用後の実増加量／試作上限を一覧表示する。プレビューとdomainの昇格処理は同じ純粋計算ヘルパーを使い、表示値と確定値の計算差異を避ける。
- 最大HPと現在HP、Lv.10等の現在レベルからLv.1への変化、EXP端数保持、証1個の消費数、移動種別／移動力、武器適性、装備中武器、昇格後の行動消費を確認前に表示する。HPは最大HPのみ加算し、現在HPは回復しない。
- 仮上限を既に超えている既存能力は減少させず、現在値を維持することをプレビューにも表示する。能力ボーナス・上限は試作値であり、正式バランスとして扱わない。
- CP-15の表示要件は採択済み。仮ボーナス・仮上限を使う現在の確認画面は、最終数値・正式なクラス別性能が決定した時点で表示内容と値の出典を再確認する。
- キャンセルはGameState・IndexedDB・UI選択状態を変更しない。
- 確定時だけapplication commandを実行し、既存の保存エラー表示・入力ロックと整合させる。
- スマートフォン幅で確認文・能力差分・ボタンが操作可能であることを確認する。

### Stage 4 — アイテム配布と章進行

- 決定された配布元・章・受取人・数量だけをcontent/reward dataへ設定する。
- 既存の章報酬validator、所持品枠数、控え名簿、章間引き継ぎを再利用し、配布失敗でアイテムを消失させない。
- 初期状態への仮配布を正式配布ルールと混同しない。旧セーブへ自動付与する場合は別途migrationとして設計・承認する。

## 7. 開発専用の合成fixture試験室

Vite開発サーバーで `npm run dev` を起動し、`http://localhost:5173/?promotion-lab=1` を開くと、7経路×3合成profileのstat previewを確認できる。これは `import.meta.env.DEV` でのみ有効な独立画面であり、本番ビルドではクエリを指定しても表示されない。試験室は `src/test-support/class-promotion-balance-scenarios.ts` の固定fixtureだけを読み取り、キャンペーンUI、GameState、RNG、IndexedDB、自動保存、セーブ形式を変更しない。合成値はdomain計算の再現性確認用であり、実プレイ21ケースの記録や数値バランスの承認を代替しない。

## 8. 開発専用の実セーブsnapshot比較ベンチ

Vite開発サーバーの `http://localhost:5173/?promotion-snapshots=1` では、アプリのセーブ管理から書き出したJSONを複数読み込み、実際のユニットsnapshotを比較できる。

- 対応形式はportable envelope version 1内の `GameStateSnapshot.saveVersion: 4`。章IDを既存章registryで解決し、現在のmap definitionに対して `isValidGameStateSnapshot` を適用する。不正なJSON、未対応version、未登録章、validator不合格は拒否する。
- 対象はsnapshot内の出撃中の味方で、現行7基本職、Lv.10以上のユニット。比較コマンドを実行するには自軍フェイズ、未移動・未行動、証を追加できる所持品空き（または証を既に所持）が必要。条件を満たさない候補は理由を表示する。
- 同一クラスの読み込みsnapshotが3件以上ある場合、各能力の同クラス内順位の平均を参考percentileとして表示する。3件未満は「分布データ不足」とし、low／median／highを自動選択しない。ユーザーは試験記録で候補を判断する。
- controlは読み込んだ元snapshot、promotionは同じsnapshotから作る切り離しコピーに既存 `performClassChange` を実行した結果。セーブに証がない場合はコピー内だけに試験用 `promotion_seal` を一時追加して消費する。これはCP-13の報酬決定でも、実セーブへの付与でもない。
- UIは能力8項目、要求ボーナス／実増加／仮上限、クラス・Lv・EXP、最大／現在HP、移動／武器／装備、行動消費、RNG不変を表示する。PR #82では既存 `performAttack` を再利用した単一seedの戦闘比較、PR #83では20／100／250seedの独立単発戦闘集計を追加した。作業中PR #86では、同じsnapshot・seedから既存 `beginEnemyPhase`／`runEnemyPhase` を使う敵軍phase 1回のpaired比較も追加している。敵行動数／攻撃数、選択ユニット標的率・被害・生存率、味方全体被害／撃破、全滅率、次phase進行率を表示する。
- 読み込んだファイルと候補はReactのメモリだけに保持し、IndexedDB・GameState・自動保存・saveVersionを読み書きしない。ネットワーク送信や永続キャッシュも行わない。リロードまたは破棄操作で消去する。これは開発サーバー専用で、本番ビルドでは表示されない。

単発攻撃のseed反復は移動・敵軍phase・複数turnを含まない。PR #86の敵軍phase比較は既存敵AIの行動を1 phaseだけ再現し、controlは行動を見送る枝であるため、昇格せず別の行動を選んだ場合との比較ではない。いずれも候補整理と既存ロジック上の影響確認を補助するものであり、実際のプレイヤー操作を含む完全な戦闘／章攻略、統制した実プレイ21ケース、CP-04／05の数値承認を代替しない。

## 9. 今回の範囲外

数値ボーナス・クラス別上限・具体的な章報酬／受取人／数量は未決定のままとする。`docs/game-design.md` 原文、セーブ形式、依存関係は変更しない。現在の仮ボーナス・仮上限を正式バランスとして扱わない。昇格時の行動消費と証の初期自動付与廃止は、採択済みの非数値ベースラインに沿った実装である。
