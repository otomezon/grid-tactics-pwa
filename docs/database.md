# データ保存設計

## 1. ステータス

添付設計書 v1.0 は IndexedDB による自動保存を提案しています。初回監査時のリポジトリは空であり、その後 `main` に追加されたのは設計・開発ドキュメントのみです。IndexedDB接続、Object Store、インデックス、実際のレコード形式、トランザクション、マイグレーションコードは確認できません。以下は**論理的な保存要件**であり、実DBスキーマではありません。

## 2. 保存方式（提案）

- ブラウザ内 IndexedDB
- セーブデータに `saveVersion` を保持
- 仕様変更時は明示的なマイグレーションを用意
- 読み込み不能時はバックアップを保持してからエラー表示
- 保存処理失敗時はユーザーへ通知し、可能なら直前の正常セーブを保持

## 3. 保存対象（設計書記載）

| 論理項目 | 保存内容 | 備考 |
|---|---|---|
| バージョン | `saveVersion` | セーブ形式の移行判定 |
| 進行 | 現在の章・ステージ | 章選択／再開 |
| 戦闘進行 | フェイズ・ターン | `player` / `enemy` 等のゲーム状態 |
| 味方ユニット | 能力、HP、経験値、クラス、所持品、位置、行動状態 | 設計書のユニット状態 |
| 敵ユニット | 敵の状態 | 再開時の戦闘再構成に必要 |
| マップイベント | イベント進行状況 | イベントの再実行防止 |
| 解放状態 | 解放済みステージ | キャンペーン進行 |
| 乱数 | RNG状態、またはシードと消費位置 | ロード後の再現性 |
| 保存情報 | 最終保存日時 | 保存状態の表示・診断 |

## 4. ゲーム状態モデル（概念）

設計書が挙げる主な状態項目:

- `phase`: `player` または `enemy`
- `turn`: 現在ターン
- `selectedUnitId`: 選択中ユニット
- `units`: 全ユニット状態
- `map`: 地形とイベント情報
- `chapterId`: 現在の章
- `battleStatus`: `preparation` / `playing` / `victory` / `defeat`
- `rngState`: 乱数状態

これは概念上のゲーム状態です。IndexedDBのObject Store名、キー、正規化方法、インデックス構成を確定するものではありません。

## 5. 自動保存タイミング（提案）

- ユニットの行動確定後
- 自軍フェイズ終了時
- 敵軍フェイズ終了時
- レベルアップ／クラスチェンジ確定後
- ステージクリア時

書き込みの一貫性、トランザクション境界、連続保存の制御、容量超過時の挙動は未設計です。

## 6. マイグレーション・障害時の要件

- `saveVersion`で保存形式を識別する。
- 新形式への変換を段階的・検証可能にする。
- 変換前のデータを保全し、マイグレーション失敗時に元データを失わない。
- 想定外の古い／新しい形式を無言で破壊しない。
- 保存失敗とロード失敗をUIから利用者に明示する。

## 7. 未決定事項

- Object Storeとレコードの粒度。
- 1スロット／複数スロット／バックアップ世代の扱い。
- トランザクション設計、保存中にタブが閉じられた場合の復旧。
- RNGアルゴリズムと状態のシリアライズ形式。
- スキーマ検証方式とマイグレーション方針。
- セーブデータのエクスポート／インポートを提供するか。
- IndexedDB容量不足・ブラウザのストレージ削除・プライベートモード時の挙動。
